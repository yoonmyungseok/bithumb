# 운영 및 관측성 설계

빗썸, 업비트, 통합 대시보드는 독립 프로세스로 구동한다. 통합 대시보드는 표시 목적으로만 합산하며 거래소별 탭과 내부 API 범위는 유지한다. 민감한 키, 시크릿, 토큰, 계좌·주문 식별자는 API·로그·대시보드에 노출하지 않는다.

- API·Gemini 텔레메트리는 거래소별 호출량, 쿼터, 실패, 폴백, 캐시 적중을 분리해 기록하며, 일일 쿼터 안전선은 95%(평시) 및 98%(긴급 탈출)로 관리한다. 쿼터 소진으로 등록된 쿨다운은 임계치 상향이나 PT 자정 롤오버 시 자동 해제된다. 대시보드 UI는 구글 콘솔(Google AI Studio)의 RPD 집계 기준과 직관적으로 일치하도록 성공한 유효 호출량(`api_success`)을 주 지표로 표기하며, 구글 429 방어를 위한 총 HTTP 시도량과 오류 건수를 별도로 투명하게 병기한다.
- 사이클 관측성은 REST 대사, 포트폴리오, 후보 탐색, 캔들 조회, AI 분석, 주문 처리의 지연을 집계한다.
- Provider 키 누락·AI 실패·스키마 실패는 신규 BUY만 차단하고, 기존 포지션 보호와 REST 대사는 계속한다.
- Public 가격 스트림 복구만으로 Private 주문·체결 정상화를 판단하지 않는다. 재연결 뒤 구독 상태와 REST 대사를 확인한다.
- 워치독은 거래소별 하트비트, stale 상태, crash-loop를 감시한다. 재시작과 실거래 활성화는 문서 변경과 별도의 운영 승인 사항이다.
- 대시보드 UI는 데스크톱 고밀도 다단 테이블과 스마트폰(sm 미만) 전용 반응형 카드 뷰(Card layout & Accordion)를 하이브리드로 지원한다. 모바일 환경에서 긴급 전량 매도 오터치를 방지하기 위해 터치 타겟과 간격을 분리하며, TradingView 차트 모달과 Canvas 성능 차트는 화면 회전(resize)에 즉시 반응하도록 설계되었다.
- 런타임 설정 매니저(`CommonConfigManager`)는 `MAX_ALT_ALLOC_PCT`, `MIN_ALT_ALLOC_PCT`뿐 아니라 AI 진입/스크리너 캐시 주기 및 사이클당 최대 AI 분석 후보 수(`MAX_AI_CANDIDATES_PER_CYCLE`)도 지원하여 대시보드 및 내부 API를 통해 봇 무중단 핫 리로드로 실시간 동적 조정 및 관측할 수 있다.
- 확정 체결 기준 운영 리포트(`src/confirmed_fill_performance.py`)는 주문 저널의 실제 체결량(`processed_executed_volume`)과 수수료만을 바탕으로 실현 레그 및 순손익(Net PnL)을 산출한다. 매도 주문에 대응하는 매수 주문 매칭 시 이미 이전 청산으로 전량 소진된 과거 매수 주문의 중복 매칭을 방지(체결 가용 수량 추적)하고, 매도 시각 이전의 유효 매수 주문이 없는 외부/수동 보유분 청산에 대해서는 매도 주문에 보존된 실제 계좌 평단가(`avg_buy_price`)를 기준 진입가로 채택하여 대시보드 최근 완료 거래 내역과의 손익 왜곡을 방지한다.
- 독립 리포팅 스크립트(`scripts/daily_performance_report.py`)를 통해 대화창이나 터미널에서 언제든 직전 24시간 양 거래소 비교 정밀 마크다운 보고서(`reports/daily_quant_report_YYYYMMDD.md`)를 즉시 생성·보관할 수 있다.

상세 작업 규칙은 [대시보드·운영 규칙](../agent-rules/dashboard-operations.md)을 따른다.

## macOS 개별 재시작

- 프로젝트 루트의 `./restart_dashboard.sh`, `./restart_bithumb.sh`, `./restart_upbit.sh`는 해당 서비스만 종료한 뒤 `process_manager.py <서비스> start --background`로 시작하고 터미널로 복귀한다. 봇은 거래소별 워치독이 구동하므로 기존 비정상 종료 복구와 하트비트 감시가 유지된다. 대시보드는 독립 백그라운드 프로세스로 실행한다.
- 스크립트는 자신의 경로를 기준으로 프로젝트를 찾고 실행 가능한 `venv/bin/python3`, `venv/bin/python` 순으로 선택한다. 가상환경 누락 또는 종료 명령 실패 시 새 프로세스를 시작하지 않는다. Windows 전용 콘솔 PID 기록은 수행하지 않는다.
- Unix 백그라운드 프로세스는 새 세션으로 터미널의 세션·프로세스 그룹에서 분리한다. 입력은 `/dev/null`, 출력은 서비스별 기존 `logs/*_spawn.log`로 연결하고 부모의 로그 핸들은 즉시 닫는다. 스크립트는 시작 명령의 종료 코드를 전달하며 각 서비스를 같은 터미널에서 순차 실행할 수 있다.
- 상태는 `./status_all.sh`, 전체 종료는 `./stop_all.sh`, 개별 종료는 `venv/bin/python src/process_manager.py <서비스> stop`으로 수행한다. 터미널을 닫거나 셸에서 `Ctrl+C`를 누르는 것으로 이미 분리된 서비스를 종료하지 않는다. 대시보드 접속 주소는 기존 환경 설정을 유지하며 시작 로그로 확인한다.
- 백그라운드 실행은 시스템 잠자기 방지나 재부팅 후 자동 시작을 설정하지 않는다. 24시간 운영에는 전원·잠자기·네트워크 유지가 별도로 필요하며 재부팅 후 자동 시작은 별도 서비스 등록이 필요하다.

## SQLite 연결 수명과 파일 핸들 고갈 방지

- `DatabaseManager`는 거래소별 DB 경로 안에서 스레드별 연결을 재사용한다. 각 연결의 소유 `Thread` 객체를 함께 보관하고, DB 접근 전에 종료된 스레드의 연결을 닫아 DB·WAL 파일 핸들을 회수한다. 스레드 식별자 재사용으로 인한 오판을 피하며 실행 중인 스레드의 연결은 회수하지 않는다.
- SQLite 연결의 `with` 문은 커밋·롤백만 수행하므로 연결 종료를 대신하지 않는다. 대시보드 요청마다 생성되는 스레드가 끝나더라도 연결을 전역 집합에 보관하면 파일 핸들이 누적될 수 있다. 마지막으로 종료된 스레드의 연결은 다음 DB 접근 또는 명시적 `dispose()`에서 회수된다.
- 파일 핸들 고갈은 macOS에서 `Too many open files`뿐 아니라 DNS `NameResolutionError`로 나타날 수 있다. 운영 분석 시 거래소별 열린 DB·WAL 핸들 수와 별도 정상 프로세스의 DNS 조회 결과를 함께 확인한다.
- 수정본은 이미 실행 중인 프로세스에 자동 적용되지 않는다. 운영 승인을 받아 거래소별 봇을 순차적으로 정상 재시작한 뒤 DB 핸들 누적 여부, DNS·잔고 조회 복구와 REST 주문 대사를 확인한다. 재시작만으로 대사 완료나 신규 BUY 허용을 가정하지 않는다.

## 설계 문서 동반 갱신 검사

GitHub Actions는 `tools/check_design_docs.py`를 실행한다. `src/` 운영 코드가 변경되면 `changelog.md`와 최소 한 개의 설계 문서가 필요하며, 전략·주문 안전·운영·아키텍처 책임 경로는 각각 대응하는 설계 문서도 함께 변경되어야 한다. 테스트 파일만 변경한 경우에는 이 검사를 요구하지 않는다.
